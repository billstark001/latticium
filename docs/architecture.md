# Architecture and host contracts

This document preserves the durable decisions from the original architecture, packaging, DSL and host-interface discussions. It describes the implemented boundary first; proposed extensions are identified as such. For current syntax and schema-1 fields, use the [DSL reference](dsl-reference.md), not an older design sketch.

## Product boundary

Latticium is a client-side construction engine. Every Minecraft 26.2/26.3 × Fabric/NeoForge target has one main mod JAR with commands, profiles and the API. Optional, separately packaged bridges read active Litematica or Forgematica placements. The main mod does not require a schematic mod, read `.litematic` files, or install a server companion. Installation alone does not start scans or actions; a command or explicitly enabled activation starts work.

The pure `dsl-core` and `planning-core` modules compile for Java 21. Game adapters and loader entry points compile and run on Java 25. The core receives neutral IDs, positions, block states, facts and actions rather than `net.minecraft.*` or loader classes.

```text
finite scope + selection predicate + target + policy
  -> section capture and three-valued scan
  -> candidate and frozen target
  -> planner / placement oracle
  -> client action gateway
  -> server update and expected-state observation
  -> complete, retry, defer or block
```

The DSL is read-only: it describes typed sets and coordinate predicates. A profile declares scope, selection, target, activation and action limits. Action rules and native placement prediction are separate, trusted capabilities. The policy gate always applies, including when a rule proposes breaking.

## Finite scope and unknown facts

Every job has enumerable, finite bounds. Complement (`!`) only produces coordinates inside that scope; `offset` and `adjacent` may read a bounded halo beyond it. Unloaded chunks, missing target data and unavailable facts remain **Unknown**. `!Unknown` remains Unknown; neither `false` nor `DontCare` is a valid substitute. `SectionScanner` represents a section with true and known masks, so a partial section cannot silently become empty.

`Host.SelectionSource.finiteBounds` returns inclusive, dimension-qualified boxes. `Host.TargetSource.target` distinguishes `Exact`, `Clear`, `DontCare` and `Unknown`. Blueprint air is returned as an exact air state by the bridge; profile `include_air` decides whether to ignore or clear it. External sources must validate their session, placement identity and bounds before answering. Conflicting overlapping subregions are Unknown.

## Sessions, actions and confirmation

A session identifies one preview or job and prevents stale facts from crossing worlds or job lifetimes. The client captures world facts on the game thread. Pure scanning and planning can operate on immutable snapshots; a future worker implementation must never read live `ClientLevel` off-thread. Native jobs, captures, oracles and gateways retain their client-world identity; independently held jobs terminate on world exit, and closed/cancelled gateways reject all further submissions. Before submission, the action gateway checks the current session, target, world state, inventory, reach and policy. `Accepted` means only that an interaction was sent; success requires a server block/section update and the expected state. A source predicate that becomes false after the first step must not make the already claimed candidate disappear. A destructive replacement also needs a verifiable post-break placement before its first break. The native fallback currently proves this only for plain property-free blocks on plain full-block supports; fluid-containing or directly coupled multi-block structures defer before breaking. Exact property-sensitive targets retain ordinary non-breaking interactions when those are predictable, but cannot use an unverified break fallback.

The synchronous adapters now supply observed registry, world, target, selection, inventory and rule epochs. A separate bounded revision ledger qualifies each capture, candidate and proposal with the inputs it actually reads. World identity and registry binding are mandatory; unrelated global epoch increments do not cancel independent work. State/fluid captures use compact spatial read descriptors and actual native mutation/residency events, including local prediction and A-to-B-to-A changes. Unknown or evicted evidence invalidates a lease. Opaque collision/player/inventory inputs and external source markers remain short-lived and are resampled before action. The section adapter captures requested columns into immutable dense `FactWindow` values; planning captures a candidate window. Optional immutable target slices share the point-read contract and fall back when unavailable. These contracts prepare an evidence boundary; native worker planning and frontier reuse remain disabled.

The executable JSON catalogs in `planning-core/src/main/resources/latticium/` define revision events, proposal reads and receipt transitions. Compiler fact columns/offsets combine with actual clicked support positions and pre-break placement proofs. Profile dependency extensions only widen required reads. [Execution options](execution-options.md) expose cell/section granularity, selection/rule stop or freeze, live/per-cell pinned targets, relevant/hotbar/full inventory checks, and conservative or settling/repeating work. Each confirmed qualified step requires fresh planning for the remainder; handing an old controller a newly captured snapshot cannot replace its original proposal evidence.

## Extension contract

The public blueprint entry point is `LatticiumClient.registerBlueprintProvider(ResourceId, BlueprintProvider)`, where `BlueprintProvider` combines the neutral selection and target interfaces. Registration occurs during loader client initialization, before profiles bind to a source ID. The bridge stays read-only and cannot replace the action gateway. The [bridge development guide](bridge-development.md) gives implementation and test steps.

The original discussions also considered a larger capability catalog, symbolic/offline binding, rule-source registry, worker planning and a general mod SPI. Those are design directions, not currently supported Java APIs. The implemented DSL remains intentionally bounded: no arbitrary script execution, recursive functions, action calls or unbounded world query. New primitives must specify type, locality, facts, invalidation and cost before entering the section scanner.

## Binding, job state and resource budgets

Parsing is independent of Minecraft: resource IDs, tags and block properties remain symbolic until a game registry is available. The binder validates those symbols against the current registry and reports missing or invalid values rather than treating them as an empty set. A future capability catalog can expose signatures to offline tools without loading a game client, but offline type checking cannot claim a resource exists in a particular world. Registry/tag reload invalidates native job and automatic profile bindings. Restart a manual job after reload; automatic profiles sample newly bound predicates using their normal initial/while behavior.

User profiles are declarative JSON, not scripts. Activation is opt-in. `enter` reacts to a known outside-to-inside transition; `while` remains active while its predicate is known true. Unknown samples cannot create an edge. A player-relative scope freezes its anchor for a scan fragment and is refreshed after movement or explicit `/latticium refresh`. Persist profile definitions, enabled flags and saved selections by world and dimension. Local worlds are identified by their normalized save directory, not their display name; do not persist unconfirmed packets or assume an old action succeeded after reconnection.

The pure `Planner.start` / `Search.advance` API preserves a Dijkstra frontier across bounded work slices; `pending()` distinguishes a resumable work-budget deferral from a terminal lack of facts. A search retains at most 65,536 states/frontier entries and releases them on a terminal result. Its oracle must read one frozen input view, and a host must discard it on relevant changes. The synchronous `plan` API performs one slice. Native jobs use `AdaptivePlanner`: a budget-limited candidate retries with 128, 256, 512 and at most 1,024 node expansions. Every retry captures fresh facts and creates a fresh search; only scheduling metadata is retained, with at most 256 retry budgets. Diagnostic searches share that tick's 1,024-expansion cap. Changed current state, target or remaining policy resets the starting budget. A path beyond the final cap stays Deferred and cannot authorize a break fallback. Full cross-tick frontier reuse still requires trustworthy immutable prediction inputs and revision tracking. Unrepresentable accumulated material/risk costs also defer instead of proving NoPlan; action counts exceeding policy are discarded before addition.

Native confirmation records the authoritative state carried by each block/section update packet, independently of the state visible in `ClientLevel`. Vanilla prediction can temporarily hide the packet state. A receipt confirms only when a newer packet carries the submitted result and that result is visible in the current world. A newer third-state payload contradicts the receipt even if local prediction still displays the expected block. An initial-state payload cannot confirm a prediction. The bounded 16,384-entry `ServerUpdates` history is keyed by position, so an unrelated update cannot confirm or invalidate an independent action. Forgotten payloads remain unavailable and can time out. The legacy one-argument block-update notification is a refresh hint, not confirmation evidence. Target sources are rechecked while observing as well as before submission; nulls and provider failures remain Unknown. Terminating a break receipt stops continued destruction.

Before an exact replacement breaks its source, the placement proof also applies the profile's material predicate in a post-break `StateOverlay`. This establishes air at the candidate and leaves uncertain derived facts Unknown. A matching item forbidden by `target.using` cannot authorize the destructive first step. The qualification retains the future placement's actual support. After confirmation, the candidate retains its target and confirmed state and replans against fresh inputs. Stable tasks block after an intervening state change; opt-in settling tasks wait and require fresh selection eligibility. Unsupported or throwing primary/post-break predictors defer without licensing destruction.

The job controller retains claimed candidates and frozen targets across a multi-step attempt. A source predicate may stop matching after a break even though the target is unfinished. Cancellation and world exit stop new submissions; an already submitted action needs its receipt settled or discarded according to session lifetime. A policy limits per-tick actions and per-activation actions, and default breaking is denied. The scanner has finite section budgets and reports partial preview/query results explicitly.

The candidate store has an independent configurable capacity (default 4,096), separate from the retry-budget cache (default 256). Admission favors nearby work and rotates deferred unstarted work; confirmed progress and explicitly pinned targets reserve capacity. Saturated sections stay parked for rediscovery. Satisfied cells use compact per-section masks within the finite domain, so rescanning cannot fill the queue with already completed work. Among ready candidates, least recently attempted work gets an opportunity before a one-tick retry may run again; proximity breaks ties. Diagnostic position samples are bounded by candidate capacity. Increasing a capacity changes retained memory; node caps alone never establish a frame-time guarantee.

Each `Compiler.Bound` includes `FactDependencies` for state, biome, fluid, light, solidity, target, player, inventory and named selections, plus its spatial read radius. Known built-ins carry per-column offsets through `offset` and `adjacent`; column masks capture only those shifted cells. For example, a player sphere does not widen a current-state read, and `surface()` needs the center and six faces rather than the full halo cube. More than 512 distinct offsets, overflow, or opaque primitive behavior falls back to the bounded halo. Boolean expressions union requirements; declarations and expanded functions retain them. Registry literals and coordinate-only predicates need no world columns. `Primitive.dependencies()` describes direct columns; the binder conservatively broadens opaque primitive/argument spatial behavior within the declared radius and freezes metadata at registration. The default for a custom primitive or a three-argument `Bound` is all facts, preserving conservative behavior. Hosts must leave unavailable or unrequested columns Unknown. A chunk without captured world data does not prevent a coordinate branch from deciding the predicate. Event refresh derives spatial world reads from expanded bound metadata; syntax analysis is retained for player-sphere geometry and falls back conservatively for opaque player dependencies. Named selection snapshots copy every bounds list so caller edits cannot alter a running job. Scan requests combine scope and selection requirements; planning adds the current state and material/target-set requirements. Optional target slices validate blueprint metadata once per window. Consecutive `adjacent` unions evaluate each reachable offset once. Mixed spatial expressions share a short-lived graph memo keyed by bound identity and position, capped at 65,536 evaluations; exhaustion stays Unknown. Integer-edge paths retain intermediate-overflow behavior. Memo entries never cross snapshots or top-level calls. The next optimization steps are palette/coordinate mask evaluation and measuring larger loaded scopes. Overlapping finite boxes first union their section domains, then evaluate each covered cell once. Grouping deduplicates boxes and caps box/section contributions at 1,000,000. A section is 16³ cells; known and true masks preserve three-valued logic. Coordinates, palette filtering and cheap predicates can run before expensive target or placement calls as long as the result is equivalent under Unknown. Main-thread capture time, allocation, scan throughput, cache invalidation, planner work and confirmation latency should be measured separately. Worker planning requires immutable leased snapshots and real revisions first.

## Validation and releases

Core tests validate DSL, profile, scanner, planner and fake-host behavior. Compilation and title-screen launches establish packaging and startup only. The [validation matrix](26.2-26.3-validation.md) records in-world interaction and bridge cases separately. Four main JARs and three validated bridge JARs are collected by the [release process](releasing.md); NeoForge 26.3 has no validated blueprint bridge.
